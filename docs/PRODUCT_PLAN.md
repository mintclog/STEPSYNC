# STEPSYNC 서비스 기획서

> **STEPSYNC**  
> **Music for your pace.**
>
> 사용자의 최근 3~5회 러닝 기록과 이번 러닝의 목표 거리·목표 페이스를 분석해, 목표 페이스 유지에 도움이 될 가능성이 높은 음악을 AI가 추천하는 반응형 웹서비스.

---

## 1. 문서 목적과 결정 원칙

이 문서는 지금까지의 대화에서 결정된 STEPSYNC의 제품 방향을 정리한다.

### 결정 해석 원칙

- 사용자가 직접 지정한 내용은 확정사항으로 본다.
- 대화 중 제안된 내용 중 사용자가 반박하거나 다른 방향으로 수정하지 않은 내용도 확정사항으로 본다.
- 서로 충돌하는 내용은 사용자의 최신 직접 결정이 우선한다.
- 여러 대안을 동시에 제안했지만 하나를 고르지 않은 경우에는 첫 번째 추천안 또는 가장 강하게 추천한 안을 기본안으로 사용한다.
- 기술적 제약 때문에 아직 실제 제공자를 정할 수 없는 항목은 예외적으로 `추가 결정 필요`로 둔다.

## 2. 제품 정의

### 2.1 서비스명

**STEPSYNC**

- `STEP` + `SYNC`
- 러닝의 발걸음과 음악의 리듬을 맞춘다는 의미

### 2.2 태그라인

**Music for your pace.**

보조 카피로 **Run in rhythm.**을 사용한다.

### 2.3 서비스 형태

**PC와 모바일 모두에서 사용할 수 있는 반응형 웹서비스**로 만든다.

- 모바일과 PC에서 동일한 핵심 기능을 제공한다.
- 화면 크기와 입력 환경에 맞게 UI를 최적화한다.
- 구현은 **Mobile-first responsive design**을 기본 원칙으로 한다.

### 2.4 핵심 사용자 프로세스

STEPSYNC의 핵심 프로세스는 다음 **3단계**다.

1. **최근 3~5회의 러닝 기록을 입력한다.**
2. **이번에 달릴 목표 거리와 목표 페이스를 입력한다.**
3. **AI가 기록과 목표를 분석해 해당 페이스 유지에 도움이 될 가능성이 높은 음악을 추천한다.**

```text
최근 3~5회 러닝 기록
        ↓
이번 러닝 목표
- 목표 거리
- 목표 페이스
        ↓
OpenAI API 분석
        ↓
목표 페이스 유지에 적합한 음악 추천
```

음악 취향은 추천을 개인화하기 위한 **선택 입력**이다. 음악 취향을 입력하지 않아도 핵심 추천 프로세스를 완료할 수 있어야 한다.

### 2.5 서비스가 하지 않는 것

STEPSYNC는 **음악 스트리밍 서비스가 아니다.**

- 음악을 직접 스트리밍하지 않는다.
- 음악 파일을 저장·배포하지 않는다.
- 러닝 중 음악을 실시간으로 변경하지 않는다.
- 실시간 페이스에 따라 음악 재생을 제어하지 않는다.
- Spotify·Apple Music 등의 재생 기능을 대체하지 않는다.

서비스의 핵심 산출물은 **개인화된 추천 음악 목록**이다.

## 3. 문제 정의와 연구 기반 가설

목표 페이스를 정하고 달리더라도 실제 러닝에서는 페이스가 흔들릴 수 있다.

음악의 BPM과 비트는 러닝 케이던스에 영향을 줄 수 있지만, **음악 BPM과 러닝 페이스는 단순한 1:1 관계가 아니다.** 속도는 케이던스와 보폭의 조합으로 만들어지며 개인마다 음악에 반응하는 방식도 다르다.

따라서 STEPSYNC는 단순한 `목표 페이스 → 고정 BPM` 변환기가 아니라 다음을 수행한다.

- 사용자의 최근 3~5회 실제 러닝 기록에서 페이스·케이던스 관계를 분석한다.
- 이번에 달릴 **목표 거리**를 함께 고려한다.
- 목표 페이스에서 적합할 가능성이 높은 리듬 범위를 추론한다.
- 사용자 음악 취향이 있다면 추천에 반영한다.
- 실제 곡의 BPM 등 음악 메타데이터를 확인한다.
- 데이터가 충분한 경우 평균 페이스뿐 아니라 **Pace Stability(목표 페이스 유지 안정성)**도 중요하게 본다.

제품의 핵심 질문은 다음과 같다.

> **“이 사용자가 이 거리를 원하는 페이스로 안정적으로 달리는 데 어떤 음악이 도움이 될 가능성이 높은가?”**

## 4. 핵심 입력 데이터

### 4.1 최근 러닝 기록 — 3~5회

AI 분석에 사용하는 기본 러닝 이력은 **최근 3~5회**다.

- 최소 분석 단위: 3회
- 최대 기본 분석 단위: 5회
- 기본값: 가능한 경우 최근 5회
- 5회보다 많은 기록을 가져온 경우 기본 분석에는 가장 최근 기록을 우선 사용한다.
- 목표 거리와 비슷한 기록이 최근 3~5회 안에 있다면 AI가 해당 기록의 맥락을 더 중요하게 해석할 수 있다.

각 러닝 기록에서 사용할 수 있는 데이터:

**기본**

- 거리
- 운동 시간 또는 평균 페이스

**강력 권장**

- 평균 케이던스

**선택**

- 평균 심박수
- 러닝 날짜
- 고도/상승고도
- 러닝 유형
- 구간별 페이스·케이던스

#### 데이터 품질 원칙

모든 입력 방식에서 케이던스나 구간별 데이터가 반드시 존재한다고 가정하지 않는다.

- 케이던스가 없으면 AI는 개인의 정확한 페이스-케이던스 관계를 임의로 만들어내지 않는다.
- 구간별 페이스가 없으면 해당 러닝의 Pace Stability를 정밀 계산하지 않는다.
- 정보가 부족한 경우 사용할 수 있는 데이터만으로 추천하되 **분석 신뢰도를 낮게 표시**한다.
- 데이터가 풍부할수록 개인화된 BPM·리듬 추론의 비중을 높인다.

### 4.2 이번 러닝 목표 — 목표 거리

사용자는 이번에 달릴 **목표 거리**를 입력한다.

예:

```text
목표 거리
10.0 km
```

목표 거리는 추천 맥락을 결정하는 핵심 입력이다.

같은 `5:30/km`라도 3km와 10km는 요구되는 지속 시간과 운동 강도가 다르므로 AI는 목표 거리를 함께 고려해야 한다.

### 4.3 이번 러닝 목표 — 목표 페이스

사용자는 이번 러닝에서 유지하고 싶은 **목표 페이스**를 입력한다.

예:

```text
목표 페이스
5:30 /km
```

코드는 목표 거리와 목표 페이스를 이용해 **예상 러닝 시간**을 계산할 수 있다.

예:

```text
목표 거리      10 km
목표 페이스    5:30 /km
예상 시간      55:00
```

이 값은 AI가 목표 러닝의 지속 시간과 강도를 이해하는 보조 정보로 사용한다.

## 5. 러닝 기록 입력 방식

러닝 기록 입력 방식은 다음 **3가지로 확정**한다.

1. **서비스 연동**
2. **스크린샷 업로드**
3. **직접 입력**

FIT / TCX / GPX 파일 업로드는 별도 입력 방식으로 추가하지 않는다.

세 방식으로 들어온 데이터는 최종적으로 동일한 내부 러닝 데이터 형식으로 정규화한다.

```text
서비스 연동 ─────┐
                 │
스크린샷 업로드 ─┼─→ 최근 3~5회 기록 정규화 ─→ OpenAI API 분석
                 │
직접 입력 ───────┘
```

### 5.1 서비스 연동

사용자의 러닝 기록을 외부 운동/러닝 서비스에서 자동으로 불러오는 방식이다.

#### 연동 UX

- `러닝 앱 연결하기`를 주요 입력 옵션으로 제공한다.
- 사용자가 권한을 승인하면 최근 러닝 기록을 자동으로 가져온다.
- 기본적으로 최근 5회를 불러와 분석 대상으로 사용한다.
- 실제 분석 단위는 **최근 3~5회** 범위로 유지한다.

#### Samsung Health

Samsung Health는 순수 웹서비스에서 Strava식 OAuth처럼 직접 연결하기 어렵고 Android 앱/SDK 및 배포 제약이 존재한다.

따라서 현재 정책은 다음과 같다.

- **MVP의 직접 Samsung Health 연동은 제외한다.**
- Samsung Health 사용자는 우선 스크린샷 입력으로 지원한다.
- 이후 필요성이 확인되면 Android companion app을 통한 Samsung Health 연동을 검토한다.
- 첫 번째 웹 연동 제공자는 기술 검토 후 별도 선택한다.

> `서비스 연동`이라는 입력 방식 자체는 필수지만, 첫 연동 제공자는 아직 기술 선택이 필요하다.

### 5.2 스크린샷 업로드

Samsung Health, Garmin, Strava 등 러닝/헬스 앱의 기록 화면을 업로드하는 방식이다.

사용자는 **총 3~5회의 최근 러닝 기록**이 확보되도록 기록 화면을 업로드한다.

OpenAI의 이미지 이해 기능으로 화면에서 러닝 기록을 추출하고 구조화한다.

#### 필수 UX

AI가 추출한 값은 바로 분석에 사용하지 않고 **사용자가 확인·수정할 수 있는 단계**를 반드시 거친다.

예:

```text
AI가 다음 기록을 찾았습니다.

거리            5.04 km
운동 시간       29:23
평균 페이스     5:49 /km
평균 케이던스   166 spm
평균 심박수     154 bpm

[ 맞아요 ]   [ 수정하기 ]
```

### 5.3 직접 입력

사용자는 **최근 3~5회의 러닝 기록**을 직접 입력한다.

거리·시간·페이스처럼 서로 계산 가능한 값은 웹에서 자동 계산해 입력 부담을 줄인다.

예:

- 거리 + 시간 → 평균 페이스 자동 계산
- 거리 + 평균 페이스 → 예상 시간 자동 계산

## 6. 음악 취향 입력 — 선택 사항

러닝 기록과 목표 거리·목표 페이스만으로도 추천을 받을 수 있어야 한다.

원하는 사용자는 음악 취향을 추가로 입력해 추천을 개인화할 수 있다.

선택 입력:

- 선호 장르
- 좋아하는 아티스트
- 선호하지 않는 장르
- 선호하지 않는 아티스트

초기 UI에서는 복잡한 프로필을 만들기보다 빠르게 선택할 수 있게 한다.

```text
좋아하는 음악 (선택)
[K-pop] [J-pop] [Rock] [Hip-hop] [EDM]

좋아하는 아티스트 (선택)
[                       ]

추천에서 빼고 싶은 아티스트 (선택)
[                       ]
```

## 7. OpenAI API의 역할

러닝 기록 분석과 최종 음악 추천 판단은 **OpenAI API**가 담당한다.

MVP는 **Responses API 기반**으로 설계한다.

### 7.1 러닝 기록 및 목표 분석

AI는 사용 가능한 데이터 범위 안에서 다음을 분석한다.

- 최근 3~5회의 평균 페이스 및 변화 경향
- 평균 케이던스(존재하는 경우)
- 페이스와 케이던스의 관계(충분한 데이터가 있는 경우)
- 페이스 변동성 / Pace Stability(구간 데이터가 있는 경우)
- 구간 데이터가 없을 경우 최근 3~5회 사이의 페이스 변동을 보조 지표로 사용
- 심박 정보가 있을 경우 운동 강도 맥락
- 최근 러닝 거리와 이번 목표 거리의 차이
- 목표 거리에서 목표 페이스를 유지해야 하는 예상 지속 시간
- 목표 페이스와 현재 기록의 차이
- 목표 페이스에서 예상되는 적정 케이던스 범위(근거 데이터가 충분한 경우)
- 목표 페이스 유지에 적합할 가능성이 높은 음악 BPM 범위
- 입력 데이터에 따른 전체 분석 신뢰도

### 7.2 목표 거리의 활용

목표 거리는 단순 표시값이 아니라 추천 판단에 사용한다.

AI는 같은 목표 페이스라도 목표 거리에 따라 다음을 다르게 해석할 수 있다.

- 러닝 지속 시간
- 최근 기록 대비 목표의 맥락
- 추천 음악의 에너지 수준
- 페이스를 안정적으로 유지하는 데 적합한 리듬 특성

STEPSYNC는 의료적·훈련 처방을 제공하는 서비스가 아니며, 목표의 안전성이나 운동 처방을 진단하는 대신 **음악 추천 맥락을 조정하는 데 목표 거리를 활용한다.**

### 7.3 음악 리듬 추천

AI는 단순히 `목표 페이스 = 특정 BPM`으로 계산하지 않는다.

초기 추천 로직은 다음 원칙을 사용한다.

1. 사용자의 최근 페이스-케이던스 관계를 우선 분석한다. 단, 케이던스 데이터가 있을 때만 개인화 근거로 사용한다.
2. 목표 거리와 목표 페이스를 함께 고려한다.
3. 충분한 개인 데이터가 있으면 목표 페이스에서 예상되는 케이던스를 범위로 추론한다.
4. 해당 케이던스와 가까운 **1:1 BPM 범위**를 기본 추천한다.
5. 두 걸음당 한 박자로 사용할 수 있는 **half-time BPM**도 후보에 포함한다.
6. 목표 페이스와의 오차뿐 아니라 데이터가 허용하는 범위에서 Pace Stability를 중요하게 평가한다.
7. 케이던스 데이터가 부족하면 일반적인 리듬 후보에서 시작하되 개인화 신뢰도가 낮음을 명시한다.

예:

```text
목표 거리        10 km
목표 페이스      5:30 /km
예상 시간        55:00
예상 케이던스    169–172 spm
추천 BPM         169–172 BPM
half-time        84.5–86 BPM
분석 신뢰도      높음
```

위 숫자는 사용자마다 달라지며, 입력 데이터가 부족한 경우 일부 값은 제공하지 않을 수 있다.

### 7.4 음악 후보 탐색 및 사실 검증

LLM의 기억만으로 곡명과 BPM을 확정하지 않는다.

MVP에서는 **OpenAI Responses API의 Web Search**를 이용해 실제 곡 후보와 BPM 등 음악 메타데이터를 탐색·검증한다.

- BPM 정보가 여러 출처에서 충돌하거나 신뢰하기 어려우면 해당 곡의 추천 신뢰도를 낮추거나 후보에서 제외한다.
- 향후 트래픽과 일관성이 중요해지면 별도 음악 메타데이터 API/DB를 추가할 수 있다.

AI는 검색된 후보를 대상으로 다음 기준으로 최종 랭킹한다.

- 목표 리듬 적합도
- 최근 러닝의 Pace Stability와의 적합도(계산 가능한 경우)
- 사용자 음악 취향(입력한 경우)
- 목표 거리·예상 지속 시간에 적합한 에너지 특성

초기 추천 가중치:

- 목표 리듬 적합도: **40%**
- 최근 러닝/Pace Stability 적합도: **30%**
- 음악 선호도: **20%**
- 목표 거리·운동 에너지 특성: **10%**

입력 데이터가 부족해 특정 요소를 계산할 수 없으면 해당 가중치를 나머지 사용 가능한 요소에 재분배한다.

이 가중치는 **MVP용 휴리스틱**이며 과학적 확률이나 효과 보장치를 의미하지 않는다. 실제 사용자 피드백과 실험 데이터에 따라 조정한다.

## 8. 추천 결과

기본적으로 **10~20곡**을 추천한다.

각 추천곡에는 다음 정보를 표시한다.

- 앨범 아트
- 곡명
- 아티스트
- BPM
- Match Score
- 추천 이유

분석 결과 영역에는 추천과 별도로 **분석 신뢰도**를 표시한다.

Match Score는 추천 알고리즘 내부 기준을 UI에 정규화해 보여주는 값이며, **의학적·과학적 성공 확률을 의미하지 않는다.** 데이터가 부족한 경우 Match Score도 보수적으로 산정한다.

예:

```text
분석 신뢰도: 높음

[Album Art]
SONG TITLE
Artist

170 BPM        96% MATCH

최근 기록에서 추정한 목표 케이던스와 가까우며,
10km를 5:30/km로 달리는 목표에 적합한 리듬 후보입니다.
```

음악은 STEPSYNC에서 재생하지 않는다. 사용자가 원하는 경우 Spotify / Apple Music / YouTube Music 등 외부 음악 서비스에서 해당 곡을 검색하거나 열 수 있도록 링크를 제공한다.

## 9. Pace Stability

STEPSYNC는 단순 평균 페이스보다 **목표 페이스를 얼마나 안정적으로 유지했는지**를 중요한 지표로 본다.

예를 들어 목표가 5:30/km일 때:

```text
A: 5:29 / 5:31 / 5:30 / 5:32
B: 5:10 / 5:48 / 5:22 / 5:42
```

평균이 비슷하더라도 A가 목표 유지에 더 적합한 러닝으로 평가된다.

다만 **구간별 페이스 또는 충분한 시계열 데이터가 있을 때만 개별 러닝의 Pace Stability를 정밀 계산한다.**

- 구간 데이터가 있으면 러닝 내부의 페이스 변동성을 계산한다.
- 구간 데이터가 없으면 최근 3~5회의 평균 페이스 편차를 약한 보조 지표로 사용할 수 있다.
- 보조 지표를 개별 러닝의 실제 Pace Stability와 동일하게 취급하지 않는다.

향후 사용자가 STEPSYNC 추천 음악으로 러닝한 결과를 다시 입력하면 다음 단계부터는 **어떤 음악·BPM에서 Pace Stability가 실제로 좋아졌는지**까지 개인화 데이터로 활용한다.

추천 시스템의 장기 목적은 다음 두 가지다.

1. 목표 페이스와의 평균 오차를 줄인다.
2. 페이스 변동성을 줄인다.

## 10. 데이터 처리 원칙

### 10.1 코드가 담당하는 부분

단순하고 결정적인 계산은 웹 애플리케이션 코드에서 처리한다.

- 거리 + 시간 → 평균 페이스
- 목표 거리 + 목표 페이스 → 예상 러닝 시간
- 단위 변환
- 입력값 검증
- 3~5회 기록 수 검증
- 누락값 검사
- 세 입력 방식의 데이터 정규화
- 데이터가 있을 경우 구간별 통계 계산

### 10.2 AI가 담당하는 부분

- 최근 3~5회 러닝 패턴 해석
- 목표 거리·목표 페이스와 최근 상태의 관계 분석
- 데이터 품질 및 분석 신뢰도 판단
- 가능한 경우 적정 케이던스 및 BPM 범위 추론
- 음악 후보 평가
- 선택적으로 음악 취향 반영
- 최종 추천과 추천 이유 작성

즉 **계산 가능한 값은 코드가 계산하고, 맥락 해석과 추천 판단은 AI가 한다.**

## 11. 공통 내부 데이터 구조

세 입력 방식은 AI 호출 전에 공통 구조로 변환한다.

기본 스키마 예:

```json
{
  "source": "screenshot",
  "runs": [
    {
      "date": "2026-08-31",
      "distance_km": 5.04,
      "duration_seconds": 1763,
      "average_pace_sec_per_km": 349,
      "average_cadence": 166,
      "average_heart_rate": 154,
      "elevation_gain_m": 22,
      "run_type": "easy",
      "splits": [
        {
          "distance_km": 1,
          "pace_sec_per_km": 358,
          "cadence": 163
        }
      ]
    }
  ],
  "target_run": {
    "distance_km": 10,
    "pace_sec_per_km": 330,
    "estimated_duration_seconds": 3300
  },
  "music_preferences": {
    "genres": ["K-pop", "J-pop"],
    "liked_artists": [],
    "excluded_artists": []
  }
}
```

`runs`는 3~5개의 러닝 기록을 포함한다.

`music_preferences`는 선택값이며 입력하지 않은 경우 비어 있을 수 있다.

`source` 값:

- `integration`
- `screenshot`
- `manual`

## 12. OpenAI 출력 형식

프론트엔드에서 안정적으로 사용할 수 있도록 AI 결과는 자유 형식 텍스트가 아니라 **Structured Outputs / JSON Schema** 기반으로 받는다.

예:

```json
{
  "running_analysis": {
    "recent_run_count": 5,
    "current_pace": "6:02",
    "current_cadence": 164,
    "target_distance_km": 10,
    "target_pace": "5:30",
    "estimated_duration": "55:00",
    "recommended_cadence_min": 169,
    "recommended_cadence_max": 172,
    "pace_stability_summary": "...",
    "analysis_confidence": "high"
  },
  "music_profile": {
    "primary_bpm_min": 169,
    "primary_bpm_max": 172,
    "half_time_bpm_min": 84.5,
    "half_time_bpm_max": 86
  },
  "recommendations": [
    {
      "title": "...",
      "artist": "...",
      "bpm": 170,
      "match_score": 0.94,
      "reason": "..."
    }
  ]
}
```

데이터가 부족해 계산할 수 없는 값은 모델이 임의로 채우지 않고 스키마에서 허용한 `null` 또는 별도의 상태값으로 반환하도록 구현한다.

```text
STEPSYNC 접속
```

## 16. 향후 개인화

사용자가 추천받은 음악으로 러닝한 뒤 결과를 다시 입력하면 다음을 학습한다.

- 어떤 BPM에서 실제 케이던스가 어떻게 변하는지
- 어떤 곡에서 목표 페이스 오차가 줄었는지
- 어떤 음악에서 Pace Stability가 좋아졌는지
- 거리별로 어떤 음악 특성이 잘 맞는지
- 어떤 장르/리듬 특성이 사용자에게 잘 맞는지

이를 통해 장기적으로:

> **“당신은 10km를 5:30/km로 달릴 때 169~171 BPM의 일정한 비트에서 페이스를 가장 안정적으로 유지하는 경향이 있습니다.”**

같은 개인화된 설명을 제공한다.

## 17. 기술 원칙

- OpenAI API 키는 브라우저에 노출하지 않고 서버에서 관리한다.
- 프론트엔드가 OpenAI API를 직접 호출하지 않는다.
- 사용자 업로드 이미지와 러닝 데이터는 필요한 범위만 서버로 전달한다.
- AI 결과는 JSON Schema로 검증한다.
- 계산할 근거가 없는 러닝 지표는 AI가 추정값처럼 생성하지 않는다.
- 곡의 BPM 등 사실 데이터는 모델의 기억만 믿지 않고 검색 결과로 검증한다.
