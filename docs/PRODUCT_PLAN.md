# STEPSYNC 서비스 기획서

> **STEPSYNC**
>
> 사용자의 최근 러닝 기록과 목표 페이스를 바탕으로, 목표 페이스 유지에 도움이 될 가능성이 높은 음악을 AI가 추천하는 반응형 웹서비스.

---

## 1. 문서 목적

이 문서는 지금까지 대화에서 **확정된 STEPSYNC의 제품 방향**을 기준으로 정리한다.

대화에서 아이디어로 제안되었지만 아직 사용자가 확정하지 않은 항목은 `미확정` 또는 `검토안`으로 구분한다. 제안 사항을 확정 요구사항처럼 취급하지 않는다.

---

## 2. 현재 확정된 제품 정의

### 2.1 서비스명

**STEPSYNC**

- `STEP` + `SYNC`
- 러닝의 발걸음과 음악의 리듬을 맞춘다는 의미

### 2.2 서비스 형태

**PC와 모바일 모두에서 사용할 수 있는 반응형 웹서비스**로 만든다.

PC와 모바일은 같은 핵심 기능을 제공하며, 화면 크기와 입력 환경에 맞게 레이아웃과 조작 방식을 최적화한다.

### 2.3 핵심 기능

사용자는:

1. 최근 러닝 기록을 입력한다.
2. 원하는 목표 페이스를 입력한다.
3. OpenAI API가 러닝 기록과 목표를 분석한다.
4. OpenAI API가 목표 페이스 유지에 도움이 될 가능성이 높은 음악을 추천한다.

### 2.4 서비스가 하지 않는 것

STEPSYNC는 **음악 스트리밍 서비스가 아니다.**

현재 확정된 범위에서는:

- 음악을 직접 스트리밍하지 않는다.
- 음악 파일을 제공하지 않는다.
- 러닝 중 음악을 실시간으로 변경하지 않는다.
- 실시간 페이스에 맞춰 음악 재생을 제어하지 않는다.

서비스의 핵심 산출물은 **추천 음악 목록**이다.

---

## 3. 서비스가 해결하려는 문제

목표 페이스를 정하고 달리더라도 실제 러닝에서는 페이스가 흔들릴 수 있다.

STEPSYNC는 러닝 기록을 기반으로 사용자의 러닝 특성을 분석하고, 음악의 리듬이 러닝 케이던스와 수행에 영향을 줄 수 있다는 연구 배경을 활용해 **목표 페이스 유지에 도움이 될 만한 음악을 개인화하여 추천**하는 것을 목표로 한다.

중요한 전제는 다음과 같다.

> **러닝 페이스와 음악 BPM은 단순한 1:1 관계가 아니다.**

따라서 STEPSYNC를 `목표 페이스 → 고정 BPM` 변환기로 만들지 않고, 사용자의 실제 러닝 기록을 분석하는 AI 추천 서비스로 만든다.

---

## 4. 러닝 기록 입력 방식 — 확정

러닝 기록 입력 방식은 다음 **3가지**로 확정한다.

1. **서비스 연동**
2. **스크린샷 업로드**
3. **직접 입력**

세 방식으로 들어온 데이터는 최종적으로 동일한 러닝 기록 형식으로 정리한 뒤 AI 분석에 사용한다.

```text
서비스 연동 ─────┐
                 │
스크린샷 업로드 ─┼─→ 러닝 기록 정규화 ─→ OpenAI API 분석
                 │
직접 입력 ───────┘
```

---

## 5. 입력 방식 상세

### 5.1 서비스 연동

사용자의 러닝 기록을 외부 운동/러닝 서비스에서 가져오는 방식이다.

**연동 대상 서비스는 아직 확정하지 않았다.**

#### Samsung Health

Samsung Health를 연동 대상으로 사용할 수 있는지 논의했다.

현재 대화에서 확인한 방향은 다음과 같다.

- 순수 웹사이트에서 Strava식 웹 OAuth처럼 바로 연결하는 구조로 확정하지 않았다.
- Samsung Health 직접 연동은 구현 방식과 배포 제약을 추가 검토해야 한다.
- 따라서 **Samsung Health 연동은 현재 확정 기능이 아니다.**

스크린샷 입력을 사용하면 Samsung Health 사용자의 기록도 별도 직접 연동 없이 받을 수 있다.

### 5.2 스크린샷 업로드

사용자가 사용 중인 러닝/헬스 서비스의 기록 화면을 캡처해 업로드하는 방식이다.

예:

- Samsung Health
- 기타 러닝 앱/서비스

OpenAI API의 이미지 이해 기능을 이용해 스크린샷에서 러닝 기록을 읽어 구조화하는 방식을 기본 구현안으로 고려한다.

**권장 UX — 아직 세부 확정 전**

AI가 읽은 값은 사용자에게 한 번 보여주고 수정할 수 있게 하는 것이 안전하다.

예:

```text
거리            5.04 km
운동 시간       29:23
평균 페이스     5:49 /km
평균 케이던스   166 spm
평균 심박수     154 bpm

[ 확인 ]   [ 수정 ]
```

### 5.3 직접 입력

사용자가 러닝 기록을 직접 입력하는 방식이다.

구체적인 필드 구성은 아직 확정하지 않았다.

현재 논의된 후보는 다음과 같다.

- 거리
- 시간
- 평균 페이스
- 평균 케이던스
- 평균 심박수
- 날짜

거리·시간·페이스처럼 서로 계산 가능한 값은 웹에서 자동 계산해 입력 부담을 줄이는 방향을 고려한다.

---

## 6. 목표 페이스 입력 — 확정

사용자는 자신이 유지하고 싶은 **목표 페이스**를 입력한다.

예:

```text
목표 페이스
5:30 /km
```

이 목표값과 최근 러닝 기록이 AI 분석 및 음악 추천의 핵심 입력이다.

---

## 7. OpenAI API의 역할 — 확정

사용자의 요구에 따라 **러닝 기록 분석과 음악 추천은 OpenAI API를 사용한다.**

### 7.1 러닝 기록 분석

OpenAI API는 입력된 최근 러닝 기록과 목표 페이스를 바탕으로 사용자의 러닝 특성을 해석한다.

분석 예시는 다음과 같지만, 정확한 출력 항목은 아직 확정하지 않았다.

- 현재 러닝 페이스의 경향
- 케이던스 정보가 있을 경우 페이스와 케이던스의 관계
- 목표 페이스와 현재 기록의 차이
- 목표 페이스를 유지하기 위한 음악 리듬 조건에 대한 추론

### 7.2 음악 추천

OpenAI API는 러닝 분석 결과를 바탕으로 실제 추천곡을 선정한다.

현재 확정된 것은 **AI가 음악 추천을 담당한다는 것**까지다.

다음 요소들은 아직 별도 확정이 필요하다.

- 음악 취향을 어떤 방식으로 입력받을지
- 곡 BPM 등 음악 메타데이터를 어디서 확보할지
- 웹 검색을 사용할지, 별도 음악 API/DB를 사용할지
- 추천곡 개수
- 추천 이유나 적합도 점수를 표시할지

---

## 8. 데이터 처리 원칙

사용자가 원하는 핵심은 **OpenAI API가 러닝 기록을 분석하고 음악을 추천하는 것**이다.

다만 단순 산술과 데이터 형식 변환은 웹 애플리케이션 코드에서 처리할 수 있다.

예:

- `거리 + 시간 → 평균 페이스` 계산
- 시간/페이스 단위 변환
- 입력 데이터 형식 통일
- 누락값 검사

이러한 전처리는 AI 분석을 대체하는 것이 아니라 입력 데이터를 안정적으로 전달하기 위한 과정이다.

**러닝 패턴의 해석과 추천 판단은 OpenAI API가 담당한다.**

---

## 9. 내부 데이터 통합 방향

세 입력 방식은 AI에게 전달하기 전에 공통 구조로 변환하는 것이 좋다.

예시 구조이며 최종 스키마는 아직 확정하지 않는다.

```json
{
  "source": "screenshot",
  "runs": [
    {
      "distance_km": 5.04,
      "duration_seconds": 1763,
      "average_pace_sec_per_km": 349,
      "average_cadence": 166,
      "average_heart_rate": 154
    }
  ],
  "target_pace_sec_per_km": 330
}
```

`source` 예:

- `integration`
- `screenshot`
- `manual`

## 10. 기본 사용자 흐름

현재 확정사항만 기준으로 한 기본 흐름은 다음과 같다.

```text
STEPSYNC 접속
    ↓
최근 러닝 기록 입력
    ├─ 서비스 연동
    ├─ 스크린샷 업로드
    └─ 직접 입력
    ↓
필요 시 입력 내용 확인/수정
    ↓
목표 페이스 입력
    ↓
OpenAI API 러닝 기록 분석
    ↓
OpenAI API 음악 추천
    ↓
추천 음악 목록 표시
```

`AI 분석을 목표 페이스 입력 전/후 어느 시점에 노출할지` 등 세부 화면 순서는 UX 설계 단계에서 최종 결정한다.

## 11. 반응형 웹 요구사항 — 확정

### 11.1 공통

PC와 모바일 모두에서 다음 핵심 기능을 사용할 수 있어야 한다.

- 러닝 기록 입력 3방식
- 목표 페이스 입력
- OpenAI API 분석
- 음악 추천 결과 확인

### 11.2 모바일

대화에서 정한 방향:

- 작은 화면에서 쉽게 사용할 수 있어야 한다.
- 터치 중심 조작에 맞게 구성한다.
- 스크린샷 업로드와 숫자 입력이 편해야 한다.
- 세로 흐름을 기본으로 한다.

### 11.3 PC

대화에서 정한 방향:

- 넓은 화면을 활용해 러닝 기록과 분석 정보를 더 여유 있게 배치한다.
- 모바일과 동일한 핵심 기능을 제공한다.

정확한 breakpoint, grid, 최대 폭 등은 구현 단계에서 결정한다.

## 12. 현재 MVP에서 확정된 필수 범위

현재 대화에서 확실히 정한 MVP 핵심은 다음과 같다.

- 반응형 웹사이트
- PC + 모바일 지원
- 러닝 기록 입력 3방식
  - 연동
  - 스크린샷
  - 직접 입력
- 목표 페이스 입력
- OpenAI API 기반 러닝 기록 분석
- OpenAI API 기반 음악 추천
- 추천 음악 목록 표시
- 자체 음악 스트리밍은 하지 않음

## 13. 아직 확정하지 않은 사항

아래 항목은 논의되었거나 구현상 필요할 수 있지만 **현재 사용자 결정 사항으로 보지 않는다.**

### 입력/연동

- 최초 연동 대상 서비스
- Samsung Health 직접 연동 구현 여부
- 직접 입력의 정확한 필드
- 몇 회의 최근 러닝을 기본 분석 대상으로 사용할지
- FIT / TCX / GPX 업로드 지원 여부

### 추천 알고리즘

- 추천 케이던스를 별도 결과로 보여줄지
- 추천 BPM 범위를 어떤 공식/추론으로 정할지
- half-time BPM을 지원할지
- `Pace Stability`를 서비스 지표로 사용할지
- 사용자 러닝 결과를 다시 받아 개인화 모델을 발전시킬지

### 음악

- 음악 취향 입력 여부 및 방식
- 음악 메타데이터 소스
- OpenAI Web Search 사용 여부
- 외부 음악 서비스 링크 제공 여부
- 추천곡 개수
- 앨범 아트 표시 여부
- 추천 이유 표시 여부
- Match Score 표시 여부

### 계정/데이터

- 로그인 필요 여부
- 러닝 기록 저장 여부
- 추천 이력 저장 여부
- 개인정보 보관 기간

### 기술

- 프론트엔드/백엔드 기술 스택
- OpenAI 모델
- 데이터베이스
- 배포 환경
- PWA 여부

## 15. 제품 핵심 문장

> **STEPSYNC는 사용자의 최근 러닝 기록과 목표 페이스를 OpenAI API로 분석해, 그 페이스를 유지하는 데 도움이 될 가능성이 높은 음악을 추천하는 반응형 웹서비스다.**
